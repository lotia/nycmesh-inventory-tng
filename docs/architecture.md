# Architecture

How inventory-tng is put together and why. For running it locally see
[DEVELOPERS.md](../DEVELOPERS.md); for deploying it see
[deployment.md](deployment.md). Individual decisions, with alternatives and
trade-offs, are recorded in [decisions/](decisions/).

## Shape

```
Browser
   │
   ▼
frontend  (nginx)  ──── /api, /admin ────►  backend  (gunicorn + Django)
  static SPA assets                              │
                                                 ▼
                                          PostgreSQL 18
```

Three pieces, two of which we build as container images:

| Component | Technology | Responsibility |
| --- | --- | --- |
| Backend | Django 6.1 + Django REST Framework | Data model, API, admin interface, authorisation |
| Frontend | React 19 + MUI, built by Vite | Everything the user sees, including QR scanning |
| Database | PostgreSQL 18 | Storage |

The browser only ever talks to one origin. nginx serves the built frontend
assets and forwards `/api` and `/admin` to Django. Two consequences worth
knowing: there is no CORS configuration in production, and **no API URL is baked
into the JavaScript bundle**, so the exact same frontend image runs in every
environment.

## Relationship to MeshDB

This project deliberately mirrors the architecture of
[MeshDB](https://github.com/nycmeshnet/meshdb), NYC Mesh's member and node
database. Mirroring means people who know one can find their way around the
other, and operational knowledge transfers.

What we take from MeshDB:

- Django + Django REST Framework over PostgreSQL
- A `src/` layout with the project package (`inventory_tng`) and the domain app
  (`inventory`) side by side, `manage.py` at the root of `src/`
- gunicorn in the container, Helm chart in `infra/helm/`, deployed to k3s
- `drf-spectacular` for an OpenAPI schema, `django-filter` for query filtering

Where we deliberately differ, and why, is recorded in
[decisions/](decisions/) — including the frontend stack, linting toolchain, and
PostgreSQL driver.

We copy MeshDB's *architecture*, not its documentation or its setup procedure.

## Monorepo

Backend and frontend live in one repository so that a change spanning both — an
API field rename and the UI that consumes it — is a single reviewable commit
rather than two pull requests racing each other. See
[decisions/0001-monorepo.md](decisions/0001-monorepo.md).

Each side keeps its own native tooling: `uv` for Python, `npm` for JavaScript.
There is no monorepo build system layered on top, because two projects do not
need one.

## Backend

`backend/src/` contains:

- **`inventory_tng/`** — the project package: settings, root URLs, WSGI/ASGI
  entry points. Settings read every deployment-varying value from the
  environment via `django-environ`, with no fallback for secrets, so a
  misconfigured deployment fails at boot rather than starting insecurely.
- **`inventory/`** — the domain app. Currently holds only a health-check
  endpoint; the data model is still being designed.

The API is versioned under `/api`, documented at `/api/docs`, and its OpenAPI
schema is generated by `drf-spectacular` at `/api/schema`.

Static files are collected at image build time and served by
[whitenoise](https://whitenoise.readthedocs.io/) from the backend process. This
is only for the Django admin's own CSS and JavaScript; application assets are
the frontend's concern.

## Frontend

A static single-page application. There is no Node process in production — the
build produces plain files that nginx serves. Fewer moving parts to run, patch,
and monitor, which matters for a volunteer-operated system.

MUI supplies the component library so that contributors are assembling
well-documented components rather than writing CSS.

## Not yet built

Named here so the gaps are visible rather than surprising:

- **The inventory data model.** No models are defined yet, deliberately — the
  first schema should be designed rather than accreted.
- **The QR multi-scan flow.** The reason this project exists: scanning several
  codes into one transaction. Both the client-side scanning approach and the
  batch API are open design questions.
- **Migration from the existing Google Sheet** (15,000+ rows).
- **Authentication** beyond Django's session authentication.
- **Background jobs.** MeshDB uses Celery with Redis. Nothing here needs
  asynchronous work yet, so neither is deployed; the shape is known if that
  changes.
- **Audit history.** `django-simple-history`, as used by MeshDB, is the likely
  answer for tracking who moved what and when.

Each of these is tracked as a design issue — run `bd ready` to see the current
state.
