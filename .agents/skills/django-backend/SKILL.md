# Backend conventions

Commands (runserver, pytest, ruff, ty, migrations, `uv add`) are documented in
[DEVELOPERS.md](../../../DEVELOPERS.md#backend), style rules in
[Code style](../../../DEVELOPERS.md#code-style), annotation requirements in
[Typing](../../../DEVELOPERS.md#typing), and test and coverage requirements in
[Testing and coverage](../../../DEVELOPERS.md#testing-and-coverage). The overall design is in
[docs/architecture.md](../../../docs/architecture.md). This file covers only
conventions you cannot infer from those.

## Layout

What the two packages under `backend/src/` are for is in
[docs/architecture.md](../../../docs/architecture.md#backend); new models,
serializers, views, and tests go in the domain app, `inventory/`.

`manage.py` is at `backend/src/manage.py`, so backend commands are
`uv run python src/manage.py ...` from `backend/`. This trips people up.

## Settings

Every deployment-varying value is read from the environment through
`django-environ`, and secrets get **no default** —
[docs/architecture.md](../../../docs/architecture.md#backend) says why, and
`DJANGO_SECRET_KEY` is the pattern to copy.

When you add a variable, read it in `inventory_tng/settings.py` via `env(...)`,
then update everything that has to move with it — the full list is in
[Deployment work](../deploy/SKILL.md#what-to-keep-in-step).

## API

- Serializers and viewsets over hand-rolled views; DRF conventions throughout.
- The OpenAPI schema is generated by `drf-spectacular` — do not hand-maintain
  API documentation anywhere. How it is kept current, and when a view needs
  `@extend_schema`, is in
  [The API schema](../../../DEVELOPERS.md#the-api-schema).
- `DEFAULT_PERMISSION_CLASSES` is `IsAuthenticated` **and** `StaffWrites`, so a
  new endpoint needs a session to read and the staff flag to write, and opening
  either up is a deliberate act. Which endpoints may be open, and to whom, is
  settled in
  [decision 0012](../../../docs/decisions/0012-two-populations.md) — read it
  before naming a permission class rather than arguing the case again in a pull
  request. `inventory/permissions.py` is where the classes live, and where
  `administrators_only` answers "is this operation reserved?" for the schema
  and for `GET /api/me` alike.
- A detail endpoint over a row the list can withdraw subclasses
  `DetailView` in `inventory/views.py` rather than `RetrieveUpdateAPIView`: it
  carries the administrator-sees-retired rule, the no-`PUT` rule, and the
  re-read that keeps a written row the same shape as a read one.
- Filtering goes through `django-filter`, not ad-hoc query-parameter parsing.
- `DEFAULT_PARSER_CLASSES` is `JSONParser` alone, so a form-encoded body is a
  415 rather than a payload nobody checked. Do not add a form parser back to a
  view: the reasoning, and what a form-encoded create would silently do to
  `active`, is on the setting in `inventory_tng/settings.py`.

## Models and migrations

The catalogue and the stock ledger are implemented in `inventory/models.py`. The
entity model is documented in
[docs/data-model.md](../../../docs/data-model.md) and its rationale in
[decision 0008](../../../docs/decisions/0008-stock-ledger-transfer-graph.md);
read both before changing a model, and update the first in the same change.
Never write code that updates or deletes a ledger row: those tables are
append-only and the database itself enforces it — see
[data-model.md](../../../docs/data-model.md#where-postgresql-specific-features-are-used).

[Database and migrations](../../../DEVELOPERS.md#database-and-migrations)
covers generating and committing migrations. Two things it does not say:
`uv run pytest` fails if a model and its migrations disagree, and an applied
migration is never edited — write the next one instead, backward compatible with
the previous release, because a rollback does not revert it
(see [docs/deployment.md](../../../docs/deployment.md#rollback)).

## Typing

The rules, the commands that tell you what is missing, and the Django patterns
`ty` cannot see are all in [Typing](../../../DEVELOPERS.md#typing). Two things
that are Django-specific and not there:

- A view's `request` is `rest_framework.request.Request`, not Django's
  `HttpRequest`.
- A nested `TextChoices` class is not in scope inside `Meta`, which is evaluated
  while the enclosing class is still being built. Constraints that need one of
  its values must spell the stored string out.

## Views

Use class-based DRF views (`APIView`, viewsets), not `@api_view` functions.
Decorated functions do not match Django's `path()` overloads and `ty` rejects
them; the class-based form is the more idiomatic DRF style regardless.
