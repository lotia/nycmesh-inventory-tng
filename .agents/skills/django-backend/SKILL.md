# Backend conventions

Commands (runserver, pytest, ruff, ty, migrations, `uv add`) are documented in
[DEVELOPERS.md](../../../DEVELOPERS.md#backend), style rules in
[Code style](../../../DEVELOPERS.md#code-style), annotation requirements in
[Typing](../../../DEVELOPERS.md#typing), and test and coverage requirements in
[Testing and coverage](../../../DEVELOPERS.md#testing-and-coverage). The overall design is in
[docs/architecture.md](../../../docs/architecture.md). This file covers only
conventions you cannot infer from those.

## Layout

`backend/src/` holds two packages, mirroring MeshDB:

- `inventory_tng/` — project package: settings, root URLs, WSGI/ASGI. Rarely
  changes.
- `inventory/` — the domain app. New models, serializers, views, and tests go
  here.

`manage.py` is at `backend/src/manage.py`, so backend commands are
`uv run python src/manage.py ...` from `backend/`. This trips people up.

## Settings

Every deployment-varying value is read from the environment through
`django-environ`. When you add one:

1. Read it in `inventory_tng/settings.py` via `env(...)`.
2. Document it in [`.env.sample`](../../../.env.sample) with a comment.
3. Add it to the environment variable table in
   [docs/deployment.md](../../../docs/deployment.md) and wire it through
   `infra/helm/inventory-tng`.

Secrets get **no default**. A missing secret must raise at boot rather than fall
back to something insecure. `DJANGO_SECRET_KEY` is the pattern to copy.

## API

- Serializers and viewsets over hand-rolled views; DRF conventions throughout.
- The OpenAPI schema is generated by `drf-spectacular` — do not hand-maintain
  API documentation anywhere. See
  [The API schema](../../../DEVELOPERS.md#the-api-schema).
- Any view whose response `drf-spectacular` cannot infer needs `@extend_schema`,
  otherwise the schema lists the path with no payload and the test rejects it.
- `DEFAULT_PERMISSION_CLASSES` is `IsAuthenticated`. Opening an endpoint up is a
  deliberate act: mark it `AllowAny` explicitly and say why.
- Filtering goes through `django-filter`, not ad-hoc query-parameter parsing.

## Models and migrations

No domain models exist yet — this is deliberate, so the first schema is designed
rather than accreted. Check `bd ready` for the design issues before adding any.

Generate migrations with `makemigrations` and commit them with the model change.
`uv run pytest` fails if a model and its migrations disagree.
Never edit an applied migration. Write migrations so the previous release still
works against the new schema, because rollback does not revert them
(see [docs/deployment.md](../../../docs/deployment.md#rollback)).

## Tests

pytest with `pytest-django`, in `inventory/tests/`. Database access needs
`@pytest.mark.django_db`.

`uv run pytest` runs coverage and **fails below the threshold**, so code you add
must be tested in the same change. The thresholds and the exclusion list live in
`backend/pyproject.toml` and are explained in
[Testing and coverage](../../../DEVELOPERS.md#testing-and-coverage). Do not widen
the exclusion list to get a build passing.

Test through the API — request in, response out — rather than calling view
methods directly, so the tests survive refactoring.

## Typing

The rules, the commands that tell you what is missing, and the Django patterns
`ty` cannot see are all in [Typing](../../../DEVELOPERS.md#typing). One thing
that are Django-specific and not there:

- A view's `request` is `rest_framework.request.Request`, not Django's
  `HttpRequest`.
- A nested `TextChoices` class is not in scope inside `Meta`, which is evaluated
  while the enclosing class is still being built. Constraints that need one of
  its values must spell the stored string out.

## Views

Use class-based DRF views (`APIView`, viewsets), not `@api_view` functions.
Decorated functions do not match Django's `path()` overloads and `ty` rejects
them; the class-based form is the more idiomatic DRF style regardless.
